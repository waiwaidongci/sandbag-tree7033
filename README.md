# 河堤砂袋装载超时解释

清汀区东闸河堤防汛物资转运班，16 名装载与调度人员轮班，管理两处装车位，为东闸河堤的三个物资交接点供应砂袋。演示使用模拟台账。。仓管在叫车前登记各批次准备状态，装车领班在完装签收后回填实耗。分析员（analyst）导入批次台账并跑超时回测，复核员（reviewer）核对留出日误报、漏报和试行方案，值班调度（viewer）查看发布结果并准备交班。以往交班靠 Excel 筛出超时记录，再根据袋数逐一打电话核对。

排车台账 CSV 每批一行，含全表唯一批次编号、装车位、本地排车时间（YYYY-MM-DD HH:MM）、计划砂袋数、排班人数、叫车前预备区到位率（以该批计划袋数为分母，填 0 至 100 的整数百分比）、叫车前待装车辆数，以及车辆进位至完装签收的实耗整数分钟。 向装车班长和排车调度交付特征组代价对照、入选规则训练叶、留出批次判断路径与实耗、误报漏报明细和下一班叫车建议。

- 交班表只突出计划袋数，开装前砂袋是否到位、待装车辆有多少，要靠班长逐一追问。
- 将同一天的记录打散回测会混用相同班前排车条件，调度员难以核对规则能否延续到下一班。
- 人工交班通常只传超时清单，上夜班的人看不出某个批次为何触发提醒，也无法从漏报反查登记环节。

## 七个业务模块

1. 河堤调运总览
2. 砂袋装载台账
3. 超时规则比选
4. 批次路径追溯
5. 装车班次复核
6. 排车记录版本
7. 防汛交班分发

## 两处装车位联合比选与排车记录版本

两处装车位共用一个补袋班，同一时段预警过多会处理不过来。系统不再按四个特征组选一棵全局树，而是为每个装车位独立比选单条件预警规则：

- **分车位候选规则**：每个装车位给出「停用」与四个班前特征各自最优的深度一单条件规则。阈值取该车位相邻不同训练值的中点，每叶至少两批；同特征同训练代价取更低阈值。停用表示该车位全部转常规，仍参与联合组合比选。
- **选择日联合定型**：枚举两处装车位候选的全部可行组合（最多 5 × 5 = 25 组），按叫车时间回放选择日。每次叫车计入本批及往前严格不足一小时（<60 分钟）内已发出的预警，两处合计不超过所填「每小时预警名额」；名额内才发预警，满额批次转常规。以误报 × 1 + 漏报 × 漏报代价的总代价最低者入选，同分按「停用优先、特征列顺序、一号位优先于二号位」的固定顺序裁决。
- **留出日沿用**：定型后规则不再变动，按叫车时间和批次号发预警，满额转常规；实耗只用于超时标注与事后计分，不参与发预警决策。常量基线是预先确定的逐批对照（全批次常量预警，不占名额）。
- **分析页面**：给出入选的两条车位规则、全部可行组合的选择日代价、留出日代价（含误报/漏报/发出数）以及因满额跳过的批次清单。
- **排车记录版本化**：排车单按单号 + 版本号存储。并发更正不覆盖原记录，而是另存一条新版本并把旧草稿置为「已被新版本替代」；受理时冻结当时的规则版本、逐批规则命中结论与名额参数，之后中断恢复仍按受理时的版本和参数重放，并核对与受理结果完全一致。完装签收只锁定记录，不改变已计分数。

## 工作剧本

1. 2026 年 11 月 24 日 15:10，清汀区东闸防汛转运班查看总览，确认两处装车位的 8 日台账共 128 批，今天有 16 批。
2. 15:15，分析员导入 2026-11-24_东闸河堤砂袋装载台账.csv，抽对 SD-24-01 的 07:00 排车时间、48% 到位率和 47 分钟实耗。
3. 15:20，分析员把超时线设为 35 分钟、漏报代价设为 4、每小时预警名额设为 3。用 11 月 17 日至 22 日拟合，11 月 23 日联合比选两处装车位，11 月 24 日只做留出评估。
4. 15:23，两处装车位均以预备区到位率规则入选（一号位阈值 79.5%、二号位阈值 82%），选择日组合代价 1 点，停用与其余特征的 24 组组合全部备选。
5. 15:26，复核员查看留出日 1 误报与 1 漏报，总代价 5 点，常量基线 8 点，本批无满额跳过。抽查 SD-24-15，97% 到位率通过规则的常规分支，实耗 43 分钟，登记为漏报。
6. 15:30，复核员核对留出代价低于基线，批准下一班试行。叫车前发现到位率低于本车位阈值时先清点缺袋、补足同批砂袋、核对托盘签并复测，再叫车；同一小时两处预警合计满 3 条后，后续批次转常规。
7. 15:35，分析员导出含规则路径和实际结果的交接表，安排 16:00 投递给东闸防汛装车调度。现场排车单的并发更正按单号另存版本，受理后中断恢复仍按受理时的规则版本与名额参数重放。下一班登记试行前后到位率和完装分钟，交给班长复核。

## 算法与复核

按本地排车日期切整日组，最晚日留出，倒数第二日选模型，其余日期拟合。每个装车位分别枚举「停用」和各班前特征的深度一单条件规则，阈值取相邻不同训练值的中点，每叶至少两批。选择日枚举两处装车位候选的全部组合，在共享的每小时预警名额下按叫车时间回放，以误报加加权漏报的总代价最低者入选，同分按固定顺序裁决。选择日定型后，留出日沿用同一规则版本与名额参数，只评估入选组合与预先确定的常量基线。完装实耗只参与超时标注和回测计分。

日期少于四天、单日少于四批、装车位少于两处、任一阶段只有一种结果，或单个装车位训练批次不足四批时，提示补台账或核对超时线后重跑。批次编号重复、时间格式错误或数值越界时，按报错批次修正源表。留出日代价未低于基线时，报告结果并维持叫车顺序。 复核问题为「两处装车位入选规则在留出班次的误报、漏报、满额跳过和代价是否支持调整叫车流程？超时批次和托盘签是否已对照交接记录复核？」。每次分析绑定数据版本和参数，原始数据按规范化内容的 SHA-256 去重；每份排车记录另存规则与参数快照，中断恢复按受理时版本重放。日程针对已复核的固定结果版本，每日模式按初次投递时间每 24 小时重复。停机期间错过多次时只补一份到站内收件箱，下一次回到原时间点。

| 字段 | 含义 | 类型 |
|---|---|---|
| `batch_id` | 装载批次编号 | str |
| `planned_at` | 本地排车时间 | str |
| `loading_bay` | 装车位 | str |
| `planned_bags` | 计划砂袋数（袋） | int |
| `scheduled_loaders` | 排班装载员（人） | int |
| `ready_pct` | 预备区到位率（%） | int |
| `queued_trucks` | 待装车辆（辆） | int |
| `elapsed_min` | 装载实耗（分钟） | int |

## 启动

```sh
[ -f .env ] || cp .env.example .env
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

- Web 界面 `http://127.0.0.1:18298`
- API 文档 `http://127.0.0.1:19298/docs`
- 数据库端口 `17798`

| 账号 | 演示密码 | 工作权限 |
|---|---|---|
| analyst | analyst-demo-24 | 导入 CSV、运行分析、导出工作稿 |
| reviewer | reviewer-demo-24 | 复核、设置和停止投递、导出 |
| viewer | viewer-demo-24 | 浏览结果、导出已批准的报告、查收投递 |

原生 HTML/CSS/JavaScript 前端与 Nginx、FastAPI、Python worker、PostgreSQL 16 和 Redis 组成五服务 Compose。`backend/src/services/domain.py` 存放业务算法，`domain.json` 定义字段与验收口径，`frontend/src/pages` 为业务页面。更新任一侧源文件后，用 `docker compose up -d --build` 重建对应镜像。`backend/src/constants/enums.py` 和 `frontend/src/constants/enums.js` 定义角色及运行状态。`.env` 支持前端、API、数据库端口、演示 seed 开关和 JWT 密钥。首次部署到非演示环境时更换演示身份及 JWT/数据库凭据。

`docker compose down` 停止服务并保留数据卷。现场数据和演示结果可以在各自版本中并存。
